## Context

[T107](T107-member-avatars.md) gives everyone one deterministic avatar seeded by their `userId`.
It is a good default and it is not negotiable-by-the-user, which some people will want to change.

This is the editor. Scoped to **what `boring-avatars` can already generate** — no uploads, ever.
Accepting an image file means a file-storage mount, image validation, decompression-bomb and SVG
guards, and the permission traps that come with all of it: a materially different task,
deliberately deferred (`T091`).

**The insight that makes this a good flow rather than a dropdown.** `boring-avatars` derives
everything from three inputs — `variant` (six of them), the `name` seed, and a `colors` palette.
So the natural interface is not "pick a style from a `<select>`"; it is **a grid of live
candidates you can reroll until you like one**. Six variants × a reroll button covers a very
large space with two controls and no typing.

**And the reroll is what keeps it safe.** The seed is persisted and rendered into other members'
pages, so a free-text seed field would be stored input from one user rendered on another's
screen. Don't build one. The app generates opaque seeds itself (`nanoid` is already a dependency)
and the member picks from what it generated — so every stored value is app-produced and bounded,
and the validation question mostly disappears.

## Acceptance criteria

### The flow

- [ ] A member can open an avatar editor, see **their current avatar large**, and a **live grid of
      candidates rendered with the real component** — not illustrations of options
- [ ] All six `boring-avatars` variants are reachable: `marble` · `beam` · `pixel` · `sunset` ·
      `ring` · `bauhaus`
- [ ] A **reroll / "otra"** control generates a fresh set of candidates from new app-generated
      seeds. This is the main verb of the screen
- [ ] Candidates render at the size avatars are actually used (24–32px) **as well as** large — an
      avatar that looks good at 96px and muddy at 24px is the failure mode this screen exists to
      prevent
- [ ] Nothing is saved until the member confirms; cancelling leaves the current avatar untouched
- [ ] Resetting to the T107 default (seeded by `userId`) is always one click away

### Storage and validation

- [ ] Persisted on the user: variant, seed, and palette — **all nullable, and null means the
      T107 default**, so existing users are unaffected and the columns can be dropped without
      data loss
- [ ] **No free-text seed input anywhere.** Seeds are generated by the app; the client sends back
      one of the seeds it was offered, and the server validates shape and length regardless
- [ ] `variant` is validated against the six known names at the API boundary, and `palette`
      against a **named, curated set** — store the palette's *name*, never raw hex from a client.
      Palettes derive from the theme, same rule as T107
- [ ] A member may only change **their own** avatar. The endpoint takes the acting user from the
      session and never a user id from the body
- [ ] Co-members see the chosen avatar, so the reads that already return `displayName` carry the
      avatar fields too — and **still no email in any response**
- [ ] Zod validates the payload at the route boundary before it reaches a service, like every
      other input

### Placement

- [ ] Lives with personal settings, **not** in a group's Ajustes — an avatar is a property of the
      user, not of one group. If that means there is no personal-settings surface yet, write that
      task rather than growing this one or bolting it onto a group screen
- [ ] Works at 375px: the candidate grid is the whole point, and it has to be usable one-handed

### Tests

- [ ] An unknown `variant` or `palette` is rejected; a null value falls back to the T107 default
- [ ] One user cannot change another's avatar
- [ ] The same stored `{variant, seed, palette}` renders identically across sessions and members
- [ ] No endpoint in the flow returns an email address

## Out of scope

**Uploading an image — permanently out for v1.** Editing display name, email or password; this is
the avatar only. Per-group avatars. Animated or seasonal avatars.
